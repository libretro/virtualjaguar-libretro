# CD boot matrix

Generated by `test/tools/cd_boot_matrix.sh` -- the regression gate for CD-boot
work. Every subsequent CD-boot fix must move rows forward through the stage
taxonomy below, never backward. Do not hand-edit this table; re-run the script
and commit its output instead. `test/tools/matrix_diff.py OLD.md NEW.md` enforces
the never-backward rule against the previous tag's copy (checklist:
`docs/release-process.md`).

## How to re-run

```bash
bash test/tools/cd_boot_matrix.sh
```

Requires `test/roms/private/` populated with the CUE/CDI/ISO images and the real
Jaguar CD BIOS (`Jaguar CD BIOS.rom` in this repo's corpus; see
`test/test_cd_bios_boot.c`'s header comment for the full accepted-filename list).
In a git-worktree checkout that does not share untracked files with the main
checkout: `ln -s /path/to/main-checkout/test/roms/private test/roms/private`.
Core must be built `make TEST_EXPORTS=1` (a plain `make` strips the dlsym export
set the harnesses need -- the script auto-rebuilds if it detects this).
Env knobs: `CD_MATRIX_FRAMES` (default 3000), `CD_MATRIX_TIMEOUT` (default 120s
per title x mode), `CD_MATRIX_ROMS_ROOT` (default `test/roms/private`),
`CD_MATRIX_OUT` (output path, default `docs/cd-boot-matrix.md`),
`CD_MATRIX_LOGDIR` (raw per-run logs, default a fresh `mktemp -d`; pass a
fixed dir to keep logs across chunked invocations), and
`CD_MATRIX_MAX_RUNS` (max NEW runs per invocation, default 0 = unlimited).

Rows append incrementally with a resume guard: title x mode combos already
recorded **by the same core build** (each row carries a hidden
`<!-- build:<rev> -->` stamp) are skipped, so an interrupted sweep resumes
where it left off; rows recorded by a different build, or unstamped legacy
rows, are re-run and replaced in place rather than silently reused.
Recording rows does not itself move the stamp -- `scripts/build-id.sh`
excludes this results file from its dirty check -- so the chunks of one
sweep share a stamp and each chunk resumes where the last stopped. For
long sweeps (or agent sessions with per-command time limits), run chunked:

```bash
# ~3 runs x <=120s wall each per invocation; repeat until every line
# reports "already recorded, skipping":
CD_MATRIX_MAX_RUNS=3 CD_MATRIX_LOGDIR=/tmp/cdmx_logs bash test/tools/cd_boot_matrix.sh
```

To force a re-run of specific rows on the SAME build, delete those table
lines from the output file first -- the resume guard re-runs missing and
stale-build title x mode combos only.

## Legend

**Stage** (finest level the harness evidence supports; `?` = insufficient
evidence to classify further, never fabricated):

| Stage | Meaning |
|---|---|
| `LOAD_FAIL` | `retro_load_game()` returned false, or the harness child crashed (segfault) before producing a usable PC trace |
| `BIOS_INTRO` | Real CD BIOS executing (boot ROM cube animation, BIOS main loop/error handler, or CD-read poll code) -- has not yet handed off to the boot stub or game. In the shared `$004000`-`$007FFF` band this requires the absence of the `[CD-BOOTSTUB] Injected` handoff marker: games link code there too (Dragon's Lair at `$004000`, Myst at `$005000`), so the address alone is not evidence |
| `BOOT_STUB` | PC parked in the injected boot-stub ISR/poll-loop/data region (`$080000`-`$08FFFF`) |
| `GAME_CODE` | PC in game-owned RAM outside the BIOS/boot-stub bands (HLE: any stable multi-PC run, since HLE synthesizes past BIOS/boot-stub by design) |
| `MENU` / `IN_GAME` | Not distinguished by any current harness -- see "Headless framebuffer caveat" in CLAUDE.md. Reported as `GAME_CODE` with a note. |
| `HARNESS_HANG` | Killed at the wall-clock timeout; the harness process itself did not exit |
| `? (pc_escape)` | Final 68K PC outside every valid execute window (RAM <`$200000`, boot ROM `$E00000`-`$E1FFFF`, cart/CD BIOS `$800000`-`$8FFFFF`) -- a crash, not a reached stage |
| `? (BIOS service band ...)` | Final PC in `$0`-`$3FFF` (BIOS TOC / CD_read service code, used both by the BIOS during boot and by games after handoff). Two variants, distinct evidence strength: "PC-SET showed no game-band entries" = the visited-PC dump was checked and contains no `$090000`-`$1FFFFF` addresses (checked negative); "PC-SET suppressed, unique_pcs>32" = the harness never emitted the dump, so the game-band check could not run (undetermined) |

Score `N/1` follows the harness's own PASS/FAIL heuristic (PC stays in
RAM/BIOS/cart range, not self-looping, not thrashing among <=4 distinct PCs,
RAM has non-trivial non-zero payload) -- see `test/cd_assertions.h`. It is
informational, not the stage classification: a title can score FAIL yet still
classify as GAME_CODE (e.g. stuck in its own hardware-poll wait loop after
booting), or score PASS while stuck in a still-early BIOS/boot-stub band.
